# سند ۹: طراحی همگام‌سازی اختیاری (فاز ۶)

> نسخه: ۰٫۱ — آبان ۱۴۰۵
> وضعیت: **هستهٔ محلی آماده؛ بخش سرور مسدود تا تصمیم کارفرما و تأمین زیرساخت**

---

## ۱. خلاصه

همگام‌سازی فاز ۶ دو نیمه دارد:

| نیمه | وضعیت در مخزن | نیازمندی |
|---|---|---|
| رمزنگاری سرتاسری بستهٔ همگام (۶٫۲) | **پیاده شد** — `core/sync/SyncPackageCodec.kt` | — |
| حل تعارض قطعی (۶٫۳) | **پیاده شد** — `core/sync/SyncConflictResolver.kt` | — |
| حساب کاربری و ورود امن (۶٫۱) | طراحی‌شده، پیاده نشده | سرویس احراز هویت + تصمیم حقوقی |
| ذخیره و همگام دو-دستگاهی (۶٫۲ سمت سرور) | طراحی‌شده، پیاده نشده | سرور + ذخیره‌سازی |
| حالت خانواده (۶٫۴) | طراحی‌شده، پیاده نشده | سرور + مدل اشتراک‌گذاری |
| پنل مدیریت داده (۶٫۵) | طراحی‌شده، پیاده نشده | سرور |
| پایش و پشتیبان سرور (۶٫۶) | طراحی‌شده، پیاده نشده | سرور |

هیچ داده‌ای در این فاز به سرور جدیدی فرستاده نمی‌شود تا زمانی که زیرساخت و تصمیم حقوقی نهایی شود. کد فعلی فقط فرمت بسته و قواعد ادغام را تعریف می‌کند تا وقتی سرور آمد، سمت کلاینت آماده باشد.

---

## ۲. مدل داده

هر رکورد در بستهٔ همگام:

```kotlin
SyncRecord(
    entity = "transaction",      // نام جدول منطقی
    id = "uuid",
    updatedAtMillis = 1_700_000_000_000,
    deviceId = "device-uuid",    // فقط برای شکستن تعادل زمانی
    deleted = false,              // سنگ‌قبر (tombstone)
    payload = """{"...":"..."}""", // JSON رمزشده در لایهٔ بسته
)
```

قواعد:

- `payload` همان DTO پشتیبان است (`BackupEnvelope`)، پس هر موجودیتی که پشتیبان می‌گیرد، قابل همگام است.
- حذف، یک به‌روزرسانی است (`deleted = true` + `updatedAtMillis` جدید)؛ رکورد فیزیکی برای ۳۰ روز نگه داشته می‌شود تا حذف به دستگاه دیگر برسد.
- `deviceId` یک UUID تصادفی برای هر نصب است و هیچ شناسهٔ سخت‌افزاری نیست.

---

## ۳. بستهٔ رمزنگاری‌شده

```
SyncPackage (JSON)
   ↓ UTF-8
BackupCrypto.encrypt(plain, passphrase)   // PBKDF2-HMAC-SHA256 ۲۱۰٬۰۰۰ دور + AES-256-GCM
   ↓
header(4 magic | 1 version | salt | iv) | ciphertext | tag
```

- کلید از «عبارت همگام‌سازی» کاربر مشتق می‌شود؛ سرور فقط بایت‌های رمزشده را می‌بیند.
- کل هدر به‌عنوان AAD احراز می‌شود؛ دست‌کاری نسخه، نمک یا IV شناسایی می‌شود.
- سقف اندازه ۶۴ مگابایت و سقف ۲۰۰٬۰۰۰ رکورد برای جلوگیری از حملهٔ حافظه.
- `magic` و `schema` داخل متن رمزشده هم بررسی می‌شوند تا بستهٔ بیگانه رد شود.

## ۴. قواعد حل تعارض

مرجع: `SyncConflictResolver`.

1. `updatedAtMillis` بزرگ‌تر برنده است.
2. در تساوی زمان، سنگ‌قبر بر رکورد زنده برنده است (حذف ناخواسته بازگردانی نمی‌شود).
3. در تساوی زمان و وضعیت، `deviceId` کوچک‌تر (لغوی) برنده است.

این قواعد یک ترتیب کامل روی نسخه‌ها می‌سازند، بنابراین ادغام در هر دو دستگاه به یک نتیجه می‌رسد (همگرایی). `isInSync` فقط وقتی true است که هر دو طرف دقیقاً همان نسخه‌ها را داشته باشند؛ تساوی زمانی از دو دستگاه، تعارض واقعی است حتی اگر برنده مشخص باشد.

> محدودیت شناخته‌شده: ساعت دستگاه باید تقریباً درست باشد. اگر ساعت یک دستگاه عقب باشد، ویرایش‌های آن ممکن است در برابر دستگاه دیگر ببازند. راهکار آینده: شمارندهٔ منطقی (Lamport) در کنار زمان.

## ۵. پروتکل پیشنهادی سرور

```
POST /v1/devices/register        {deviceId, deviceName} -> {token}
GET  /v1/sync/state               -> {revision}
GET  /v1/sync/changes?since=R     -> {revision, packages:[opaque bytes]}
POST /v1/sync/changes             {baseRevision, packages:[opaque bytes]} -> {revision}
DELETE /v1/account                -> حذف همهٔ بسته‌ها و کلیدها
```

- سرور بسته‌ها را «blob مات» ذخیره می‌کند؛ هیچ رمزگشایی، ایندکس محتوایی یا جست‌وجو ندارد.
- هر حساب یک `revision` یکنوا دارد؛ همگام دو دستگاه در حالت عادی یک رفت‌وبرگشت است (< ۱۰ ثانیه در شبکهٔ معمولی).
- حذف حساب باید همهٔ بسته‌ها، متادیتا و کلیدهای سرور را در یک تراکنش پاک کند.
- برای خانواده (۶٫۴): چند `deviceId` زیر یک `groupId` با بسته‌های مشترک و کنترل دسترسی در سطح گروه.

## ۶. مدل تهدید

| تهدید | پاسخ |
|---|---|
| اپراتور سرور داده را بخواند | رمزنگاری سرتاسری؛ سرور فقط بایت می‌بیند |
| نشت پایگاه سرور | بسته‌ها بدون عبارت همگام بی‌معنا هستند |
| دست‌کاری بسته در شبکه | TLS + GCM tag و AAD |
| حملهٔ بازپخش (replay) | `revision` یکنوا + رد بسته‌های قدیمی‌تر از revision پایه |
| از دست دادن عبارت همگام | بازیابی ممکن نیست؛ در UI باید صریح هشدار داده شود |
| حذف ناقص حساب | تست پذیرش: پس از DELETE هیچ بسته‌ای در سرور نماند |

متادیتای قابل مشاهده برای سرور: اندازهٔ بسته، زمان ارسال، تعداد دستگاه‌ها. هیچ مبلغ، متن یا نامی دیده نمی‌شود.

## ۷. کارهای باقی‌مانده برای تکمیل فاز ۶

1. تصمیم کارفرما دربارهٔ میزبانی و انطباق حقوقی.
2. پیاده‌سازی سرویس ثبت دستگاه و نگهداری blob.
3. آداپتر `SyncEngine` روی مخازن (اعمال `takeRemote` با همان `upsert`های backup).
4. صفحهٔ «همگام‌سازی» در تنظیمات: ساخت عبارت، اتصال دستگاه، وضعیت آخرین همگام، قطع اتصال و حذف دادهٔ ابری.
5. تست پذیرش: دو دستگاه، ویرایش هم‌زمان یک تراکنش، همگرایی در یک دور؛ قطع شبکه در میانهٔ ارسال.
